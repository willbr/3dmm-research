# `IN_80386` audit (Project 1 task 1)

**Goal:** find every `IN_80386`-gated path in the tree, decide a portable replacement for each.

**Total:** 36 sites across 9 source files plus 3 build/doc references.

## Headline finding

Every `IN_80386` block in C++ source already has a portable C `#else` branch. **MSVC x64 cannot compile `__asm`** anyway, so on x64 we *must* take the `#else` path. The plan is therefore:

1. Stop defining `IN_80386` for non-x86 targets.
2. Fix the one site without a portable fallback (`util.h` endianness define).
3. Skip the `kcdc_386.h`/`kcd2_386.h` codegen on non-x86 (collapses Project 1 task 2 into task 1 for x64 — only x86 still needs the generated headers).

No edits needed inside the `__asm`/`#else` blocks themselves. Performance impact: negligible. The blits and `utilcopy`/`utilint` ops have had two decades of C++-compiler optimization; `gfx`/`mbmpgui` blitters run at 8-bit / 640×480 rates (~300 KB/frame), not a hot path on modern hardware.

### C. Endianness gate — needs portable replacement (1) ⚠

`kauai/src/util.h:24-26`:

```cpp
#ifdef IN_80386
#define LITTLE_ENDIAN
#endif // IN_80386
```

**This is the scariest line in the audit.** Once `IN_80386` is gone, `LITTLE_ENDIAN` won't be defined, the `BigLittle()` macros silently flip, and every chunk reader interprets bytes in the wrong order — without any diagnostic. The runtime symptom is a `.3MM` open producing garbage, blamed on bad data rather than the build.

**Fix:** detect little-endian portably. Targets we care about (Win x64, Win ARM64, macOS x86_64/ARM64, Linux x86_64/ARM64) are all little-endian. Two-line replacement:

```cpp
#if defined(__BYTE_ORDER__) && __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__
#define LITTLE_ENDIAN
#elif defined(_M_IX86) || defined(_M_AMD64) || defined(_M_ARM) || defined(_M_ARM64)
#define LITTLE_ENDIAN
#endif
```

(Project is C++14, so `<bit>`'s `std::endian` is unavailable.)

### E. `kcdc_386.h` / `kcd2_386.h` codegen — folds into task 1 for x64

`kauai/src/codkauai.cpp:469` and `:831` `#include` these generated headers, **inside `#ifdef IN_80386`**. When the define drops on x64, the headers are no longer needed for that build.

`CMakeLists.txt:170-184` runs `kcdc-386`/`kcd2-386` to generate them, and `:196-197` adds them as `target_sources` of the kauai library — both unconditional today. Both should be gated on the same x86 condition added in (A).

**Result: Project 1 task 2 ("Replace `kcdc_386.c`/`kcd2_386.c` with portable codegen, or pre-generate the headers and check them in") is unnecessary for the x64 build.** The C codec path doesn't need them. Task 2 only matters if we want to keep the x86 build alive *and* run the build from a 64-bit-only toolchain — at that point pre-generating the headers and checking them in is the cheapest answer (the generated headers are pure data, target-arch-independent). Defer until somebody actually wants that.

## Recommended commit sequence

Each independently revertible:

1. **Fix `util.h` endianness** (Section C). Land first, alone — this is the silent-correctness fix and should land before the define gate moves so x64 builds never have the broken behavior even briefly.
2. **Gate `IN_80386` define + codegen on x86** in `CMakeLists.txt` (Sections A and E). Must follow #1.
3. **Strip `setvars.bat`'s `IN_80386` line and update `CLAUDE.md`** wording (Section A leftovers). Cosmetic; can land anytime after #2.
4. **Remove the `FATAL_ERROR` in `CMakeLists.txt:53-55`** and add `x64:msvc:debug` etc. presets. This is Project 1 task 6 — listed here only to mark that it becomes legal once #1-#3 land.

Steps 1-3 should be roughly **half a day**. Step 4 will surface task 4's bare-`long`-in-on-disk-structs cascade, which is the next real piece of work and should follow the §0a item-2 geometry tests landing first.
